# 编辑与审校记录

正文：`easyagent-whitepaper.zh-CN.md`。本附件面向作者，不作为正文中的实验结果。

## 1. 写作提纲与段落职责

1. 摘要与问题定义：为什么领域化会进入运行机制。
2. 两条路线：应用框架留下的协作成本，产品二次开发留下的机制替换成本。
3. 核心思想：Harness 一级抽象、机制与实现分离、知识封装、默认入口与替换出口。
4. 具体方法：Memory / Context / MetaMessage / Session / Storage，及真实公共 API 示例。
5. 三组对比：应用与编排框架、完整 Harness 产品、模块化 Harness SDK。
6. 场景与边界：将优势落到变化任务，明确当前实现范围和选型条件。
7. 结论：把构建 Harness 变成局部可掌握的开发工作。

正文通过隐藏的 `role` 注释标记 opening、challenge、method、evidence、advantage、limitation 和 conclusion 段落组；正式阅读版不显示编辑标签。

## 3. 首轮审校：事实与范围

- 比较覆盖 17 个项目/项目家族分组、19 个官方来源；LangChain 与 LangGraph 按生态关系归为一行。
- 将 Deep Agents、Pydantic AI Harness、OpenHands SDK、Cline SDK 作为直接比较对象，而不是只对比编排框架。
- 明确 OpenAI Agents SDK 的 Sandbox Agent 能力，不沿用“没有 Harness”这一过度简化。
- Microsoft 项目按 Agent Framework 与 AutoGen / Semantic Kernel 的继承关系描述。
- Gemini CLI 的旧 architecture URL 无法作为有效来源，改用官方仓库，删除未经核对的内部包结构断言。
- 不引用反编译来源，不将第三方评估数字转移到 EasyAgent。
- 不运行实验，不改框架或 S4Code 代码；本轮仅创建文档、插图和构建工具。

## 6. 五维自检

1. **贡献是否具体？** 是：以模块契约与职责分离说明设计特色；不是抽象地宣称“模块化”。对首创性的主张已排除。
2. **表达是否清楚？** 使用统一的 Harness 定义，区分运行 API、构建契约和源码修改；通过真实接口与场景解释。
3. **实验是否支持效果？** 本版没有实验，因用户明确选择宣传白皮书。所有量化与优越性结论均未纳入。
4. **比较是否完整？** 覆盖三类主流路线，并包括最接近的模块化方案；不将概览级核对伪装成全面兼容性测试。
5. **方法是否夸大可靠性？** 已说明取消、副作用、外部任务恢复与 OS 沙箱边界；模块化不自动提供这些保证。

## 8. v0.3：框架如何承接模块，而不只说明模块边界

### 本轮提纲与段落职责

1. 第 3.1–3.2 节（method）：功能模块、默认实现和用户实现如何围绕职责契约组织。
2. 第 3.3 节（method）：安装时的绑定/注册与运行时的调用位置；显式会话操作不混入每轮循环。
3. 第 3.4–3.5 节（advantage / limitation）：逐层增加控制；无需学习无关内部机制，但需履行公开契约。
4. 第 4.1 节（opening）：模块分工表和统一的使用路径，不引入万能 BaseModule。
5. 第 4.2–4.6 节（method / evidence）：Tool、Prompt、Memory、Compactor、Session Store 的代码与责任分工。
6. 第 4.7 节（advantage）：装配已有模块后仍使用普通 Agent 入口，不再编写一次 Harness 接线。

### 主张—证据校对

| Claim | Evidence | Status |
| --- | --- | --- |
| Memory 用户无需重复注册工具与 Hook | `with_memory()` 的绑定与注册路径；正文提取代码的离线检查 | supported：限于正常安装路径 |
| Prompt 用户实现 build 即可保留模块说明合并 | `BaseSystemPromptComposer.compose()`；ResearchPrompt + EvidenceMemory 检查 | supported：主动覆盖 compose 或关闭合并时不再承诺 |
| 工具结果不需手动接入后续请求 | Tool/Registry 与默认执行管线；公开工具执行入口检查 | supported：直接 run 不等于完整 Agent 执行 |
| 压缩器作者不用重写预算与调用时序 | RequestPreparer、ContextManager、BaseHistoryCompactor | supported：自定义算法仍要输出有效内容 |
| 存储作者不必重新装配 Agent 或遍历内部模块 | SessionPersistence 与 Store 记录契约；保存/恢复检查 | supported：数据库原子版本检查属于后端责任 |
| 使用者完全不需要任何底层知识 | 不符合自定义逻辑与资源责任的事实 | removed：改为无需掌握无关内部实现和手工接入循环 |
| 默认工程实现等同于生产安全认证 | 本版没有这样的实验或认证 | removed：只说明具体机制及其边界 |

### 示例验证

七段正文代码已通过离线接口检查，覆盖导入与装配、参数校验、工具结果、提示词/记忆说明合并、Memory 工具与 Hook 注册、异步注入及临时消息回收、压缩器输出、Store 版本冲突与恢复。模型响应被替换为固定假数据，仓库只使用内存，没有执行真实 API 或数据库实验。

### 五维复核

- 贡献：以“用户写什么、框架接管什么”明确设计价值，不将类数量视为创新。
- 表达：框架内部图与产品分层图区分，代码按同一领域案例递进。
- 实验：只有文档示例检查，无性能、用户研究或任务效果结论。
- 覆盖：工具、提示词、记忆、压缩与存储均有具体例子，不只介绍最近重构的三个模块。
- 正确性：公开生命周期、异步 I/O、状态格式与所有权仍需理解；默认接入不等于任意替换都自动安全。
